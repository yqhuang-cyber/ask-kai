# 主题管理服务与在线规划时延

2026-10-15 · v1.1 · **主题服务仍为设计，逐轮 2 秒运行预算已实施**。TopicPack 提前生成并绑定主题，独立主题管理服务负责准备和发布；在线 Planner 只读取已发布包。逐轮规划总预算最多 2 秒。

## 1. 管理链路与学习链路

管理链路：管理员定义主题 → 发起生成任务 → LLM 生成 TopicPack → 自动结构／内容准入 → 可发布版本 → 发布到主题目录。

学习链路：学习者选择已发布主题 → 读取固定 TopicPack 版本与三类学习资料 → 初始化 Planner → 语音交流 → 每轮规划下一步。

两条链路分开。会话初始化、每轮规划和缓存未命中均不能调用生成器；没发布的主题不出现在可开始列表，过期／撤销／缺失返回明确不可用，不触发在线生成或默默换运动课。管理员可以查看生成状态，生成等待不计入学习会话准备时间，也不能用隐藏生成任务伪装成低延迟。

## 2. 独立服务职责

拟新增 apps/topic-manager，提供独立 HTTP 服务和最小主题管理页面；本地 POC 与 gateway 分开启动，不要求部署云服务或接生产 HSKai。模块／接口保持独立，后续可单独部署。

| 能力 | 交付 |
| --- | --- |
| 主题定义 | 稳定 topic_id、名称、brief、语言／内容范围、允许能力资源版本 |
| 生成任务 | task id、状态、超时／取消、失败原因、幂等 request id；LLM 配置仅服务端 |
| 版本预览 | 查看通过准入的材料、限制、来源、生成／review 版本；不显示 raw provider traces |
| 发布与停用 | 发布指定不可变版本、更新 active version、撤销／回滚；支持显式管理操作和有授权的自动发布 policy |
| 运行读取 | 列出可用主题、读取已发布 active 或指定版本；不提供从运行读取触发生成的 API |

管理写入与运行读取权限分开；页面不能上传任意 pack 并自称已审核。发布由宿主执行，模型不能填写 published／authorized／mastered。没有逐主题手写内容或逐包人工审批的前置要求，共用准入和抽样校准仍需落实。

TopicPack 保留 llm_generated 来源，skill／课程来源另外引用。默认不接收 learner 画像／历史；同主题基础包可供不同学习者复用，个性化由 Planner 决定。新增主题主要通过定义、生成、准入、发布完成，不新增核心 topic 名称分支。

## 3. 生命周期、持久化与消费

生成任务状态为 queued／generating／validating／succeeded／failed／cancelled；版本状态为 draft／validated 或 validated_restricted／published／revoked。任务成功不自动证明版本已经发布，published 不证明学习者掌握。仅通过准入且按所需权限发布的版本可供学习会话使用。

POC 主题定义、准入材料、不可变版本与发布索引存入独立的本机存储目录（例如 ignored .local/topic-manager），采用原子更新；gateway 缓存只加速读取，不是资源唯一来源。主题服务重启后已发布版本仍可读取；正在生成的任务恢复为中断／失败，不盲目重发未知供应商调用。

缓存 key 为 topic_id＋pack version／hash＋语言／范围＋相关 policy 版本。创建准备时核对发布／有效性；会话绑定版本，后台发布新版不改变活动会话。收到撤销后失效相关准备、暂停受影响教学，迟到提案不恢复。不得声称尚未收到的远端撤销已被即时处理。

读取未命中只从主题服务获取已发布版本；无有效资源或服务不可用时返回明确准备失败，不生成补包、不使用未知过期版本。运行请求的超时有界并计入初始化预算；会中使用已绑定包，无需每轮调用主题服务。

## 4. 生成与规划的不同预算

后台生成有独立、可配置的 deadline、重试次数与费用上限，记录生成／修复／内容检查分母；原拟议 15 秒仅作为管理任务试验起点，需按模型实测调整，不是学习者等待预算或服务 SLA。

初始化暂保留现有 10 秒上限（资料／已发布资源读取、规划、校验与提交）；提前发布移除了主题生成等待，但不能据此保证整个开始流程低延迟。另测资料读取、初始化、语音连接与首音的 P50／P95。

### 逐轮规划最多 2 秒

- 从宿主接受有效 user.final（或已接受的更正版本）开始计时，不从较晚的模型发起时刻重新计时。
- 同一个 2000ms deadline 包含排队、状态／上下文准备、模型请求与 body 读取、可选修复、Validator、保守降级和提交；跨层传递剩余时间，不重置预算。
- 通常一次精简 Planner 请求。预留提交／降级时间，模型不能用满 2 秒；例如先预留 200ms，再通过实测调整，但总上限不变。剩余不足不发起修复，也不额外同步调用 Judge 或生成器。
- 拒绝、结束、撤权、换题和打断按已有规则及时处理，不等模型。超时保守回应当前内容，记录 rule／timeout，不以降级成功充当 LLM 质量通过。
- deadline 后的模型／修复结果不能提交；新输入、取消、更正与授权变化同样隔离迟到结果。观察 shadow 如运行，仍受源话轮剩余预算限制，不延长主规划 deadline。
- 测 accepted final 到提交／取消／降级的真实耗时；出现超过 2000ms 的调度／处理 overrun 必须报告，不能只靠 timeout 配置宣称达标。

2 秒限定规划阶段，不包含 ASR 端点／转写、豆包回复生成、网络与播放。学生说完到首个可听回复仍要端到端测量。当前 next_turn_advisory 不等待 Planner 控制本轮自动生成；正式当轮门控是另一验收。

## 5. 验收重点

1. 管理端定义运动，真实或明确 mock 生成、准入并发布；没发布时学习端不能开始该主题。
2. 同一已发布包供四个学习者个性化规划；规划输入不含生成器 oracle，资料不进入共享主题存储。
3. 初始化／逐轮／缓存 miss 的生成调用数均为 0；重启、失效、撤销、服务不可用有负例。
4. 第二主题经同一管理链路发布，核心无新增主题分支；版本替换不改写活动会话／历史证据。
5. 逐轮正常、修复、超时、排队、更正和忽略 abort 的 adapter 均使用同一 2 秒预算；记录实际 overrun、LLM 完成率和语义质量，避免全部超时却称达标。

本设计通过 [TP-00～11 tasking](topic-planner-tasking.md)落实。主题服务／持久化尚未实现；2026-10-15 已修改现有运行的 2 秒预算、宿主接受输入计时、共享修复／校验截止和过期拒绝。verify 440 项、三个 synthetic replay 与 15 案离线规划契约通过；没有新模型／豆包调用，不证明真实首音达标。会中链路见 [教学设计 8.1](initial-planner-teaching-design.md#81-会中逐轮的处理链路)。
